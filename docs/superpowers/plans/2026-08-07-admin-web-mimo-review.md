## 架构评审意见

总体来看，这份方案逻辑清晰、范围明确、对现有后端能力的盘点详尽，是一个合格的启动规划。以下基于您要求的五个维度，提出具体问题与改进建议。

### 1) 遗漏的风险/缺口

*   **认证与安全风险**：方案提及“验证码(可关)”，但未明确：
    *   后端是否已有验证码生成/校验接口？若无，此功能需在M0前或并行开发。
    *   密码重置/修改、多租户数据隔离（权限模型提到SQL自动加TenantID）的校验是否完备？方案仅依赖角色，未提租户上下文。
*   **权限模型实现细节模糊**：
    *   方案提到“路由守卫 + 后端 Roles 双重校验”，但未明确**前端路由守卫**的具体策略（如：根据`/auth/me`返回的`menus`和`roles`动态生成路由？还是静态映射？）。
    *   **按钮级权限**如何实现？是前端隐藏按钮，还是后端接口返回可操作列表？方案未深入。
*   **设计文档与技术实现的“冲突处理”**：设计文档是“依据”，但实际开发中必有细节冲突（如UI组件交互、字段命名）。方案缺少一个**需求澄清与变更控制流程**，特别是当后端返回的API结构与设计文档的预期不符时，前端如何适配、谁有权决定变更。
*   **性能与体验的基线**：提到“大列表性能”，但未给出基线指标（如：列表接口响应时间目标、首屏加载时间）。这会使后续优化失去度量依据。
*   **导出功能的性能与一致性**：导出按钮“触发后端`/export/*`”是正确做法，但未考虑**大数据量导出**（如导出所有学生历史记录）的异步处理（生成文件、提供下载链接）与用户体验。前端需配合轮询或WebSocket。
*   **统一操作日志的聚合复杂度**：现有的`student-audit-log`和`course-audit-log`实体结构很可能不同（记录的实体、字段差异大）。方案中“聚合查询”可能面临性能挑战和字段统一难题，可能需要新建一个专门的`operation_log`表进行埋点记录，而非简单聚合旧表。

### 2) 技术选型问题

*   **选型合理但细节不足**：
    *   **状态管理**：Pinia选择正确，但方案中`stores/`只列了`auth`和`app`。在复杂的ERP系统中，**跨页面共享的、非用户状态的数据**（如校区列表、课程类型枚举）应集中管理，建议增加`stores/global.ts`或类似模块。
    *   **CSS解决方案**：未提及。AntD Vue 4有定制主题能力，需确定是使用Less变量覆盖，还是CSS-in-JS，或是其他方案。需在M0明确。
    *   **TypeScript的严格性**：仅提“TS类型安全”，未说明是否开启`strict`模式，以及如何规划与后端API的类型共享（如使用`openapi-typescript`或手写`api.d.ts`）。这直接影响开发效率和代码质量。
*   **技术栈一致性考量**：小程序端（`miniapp/`）与Web端使用不同技术栈（小程序原生/Vue3），在**UI组件、工具函数（如金额格式化）、业务逻辑（如状态枚举）** 上难以复用，会增加长期维护成本。虽不是本次范围，但应在文档中记为已知技术债。

### 3) 里程碑拆解问题

*   **依赖关系不清晰，可能导致前端阻塞**：
    *   **M3（教师管理）** 完全依赖缺失的后端接口（❌），是阻塞项。应明确**前端开发（页面结构、Mock数据）与后端接口开发的并行计划**，而不是简单的“后端依赖”列示。
    *   **M7（积分商城）** 同理。建议将后端接口开发前置，或明确标记为“前端先行，接口就绪后联调”。
*   **里程碑粒度与价值交付**：
    *   **M0（脚手架）** 包含登录和布局，这是核心基础，没问题。
    *   **M1（首页）** 是展示型页面，依赖现有接口，可以。
    *   **M2（学生管理）** 是核心业务，且依赖现有接口，作为首个完整业务模块合适。
    *   **但M4-M6的业务模块（班级、课程、报名、课时、请假、工资）之间存在大量数据关联**（如报名关联学生、课程、合同；课时关联班级、教师）。将它们拆得过细（M4、M5、M6）可能无法体现业务流程的完整性，也容易因接口细节问题来回修改。建议考虑按**业务域**合并，例如M3=M3a教师管理+M3b班级课程管理，M4=报名收费与课时管理核心流程。
*   **验收标准缺乏量化**：如“60s自动刷新”的验证方式（观察？自动化测试？）、“权限校验通过”的具体测试用例。建议为关键可验证目标补充具体步骤或验收标准。

### 4) 与后端现状不符之处

*   **学生详情的“9模块”**：方案假设`students/:id`返回聚合了所有9个模块的数据。但后端详情接口很可能只返回基本和核心关系数据，**反馈、积分、附件等模块可能需要独立的API调用**。方案中“部分+⚠️需补”的描述过于模糊，应在功能清单中明确指出每个子模块对应的**具体API端点或当前状态**。
*   **操作日志的“统一查询”**：如前所述，当前分散的审计日志实体可能无法直接提供“统一操作日志查询”。这不是“补一个API”那么简单，可能涉及**数据模型重构或新建中间层**。方案对此风险评估不足。
*   **导出接口的覆盖范围**：后端已有的`export/*`接口（学生、课时、消耗、工资、财务）与功能清单中的18个页面/全局能力不完全匹配。例如，**班级、课程、积分商城的导出是否支持？** 需要逐一核对功能清单所需导出项与现有接口的映射。
*   **权限控制的“数据范围”**：权限设计文档提到“SQL自动加 Tenant/TeacherID 过滤”，这要求前端在某些列表页面（如学生列表、课时列表）可能**无需传递额外的过滤参数**，后端会自动处理。但方案的功能清单和API映射中，未说明前端在何种场景下需要传递租户或教师ID（如“教师查看自己的课时”），这可能导致前端传了冗余参数或漏传必要参数。

### 5) 更优方案建议

*   **引入轻量级技术设计评审**：在“确认门”批准后，M0开始前，增加一个针对前端技术方案（项目结构、状态管理、路由设计、API类型定义、权限守卫实现伪代码）的内部评审，确保技术实现路径可行且一致。
*   **重构里程碑，体现并行与价值**：
    1.  **M0: 基础脚手架与规范**（含技术设计评审结论）。
    2.  **M1: 核心流程最小闭环**（学生列表、登录、首页）。优先交付一个可演示、可登录、可看数据的版本。
    3.  **M2: 业务域扩展A**（教师管理、班级课程管理）。此阶段并行推动后端教师CRUD、班级课程相关聚合接口的开发。
    4.  **M3: 业务域扩展B**（报名收费、课时、请假审批）。聚焦招生和教学核心闭环。
    5.  **M4: 业务域扩展C**（工资、数据统计、系统设置）。包含管理与运营模块。
    6.  **M5: 增值与收尾**（积分商城、操作日志、导出优化、权限细化）。此时大部分基础已稳定，可专注扩展和优化。
    7.  **M6: 联调、优化与部署**。
*   **明确接口契约与Mock规范**：对于M3/M5等依赖后端新接口的里程碑，强制要求在开发前，**前端与后端对齐并确认接口契约（OpenAPI/Swagger文档）**。前端使用`MSW`或`YApi`进行Mock，实现真正的并行开发。
*   **强化非功能需求**：在方案或单独文档中，补充：
    *   **性能指标**：关键列表接口P95响应时间 < 300ms，首屏加载时间 < 2s。
    *   **监控与日志**：前端接入监控（如Sentry），记录JS错误和API性能。
    *   **构建与部署**：明确构建产物（dist）、部署环境、与后端的集成方式（同域/反向代理）。
*   **建立“技术债”清单**：将已识别但本次暂不处理的项（如小程序与Web技术栈不一致、某些设计文档冲突）正式记录在案，作为未来迭代的输入。

### 总结

该方案**信息收集充分，框架正确**，但作为执行蓝图，在**风险前置、依赖管理、细节可执行性**上需要加强。建议在批准后，重点解决里程碑间的依赖阻塞问题，并补充关键技术细节的决策，以确保后续开发顺畅。
